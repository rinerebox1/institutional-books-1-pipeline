## 日本語書籍の特定

日本語の書籍データを処理する最初のステップは、主として日本語で書かれている書籍を特定することです。このパイプラインは、書籍の言語を確かめるための主要な方法を2つ提供します：メタデータによる方法と、自動言語検出による方法です。どちらの方法も、その結果を各`BookIO`エントリにリンクされた`MainLanguage`テーブルに保存します。日本語のISO 639-3コードは「jpn」です。

### 1. メタデータからの言語情報の利用

書籍によっては、ソースメタデータに言語情報が埋め込まれている場合があります。パイプラインは以下のコマンドを使用してこの情報を抽出します。

```bash
python pipeline.py analyze extract-main-language-from-metadata
```

このコマンドは、`MainLanguage`テーブルの`from_metadata_iso639_3`フィールドに値を設定します。

### 2. 自動言語検出の利用

パイプラインは、各書籍のOCRテキストを分析してその言語を検出することもできます。

```bash
python pipeline.py analyze run-language-detection
```

このコマンドは、`MainLanguage`テーブルの`from_detection_iso639_3`フィールドに、テキスト中で最も多く検出された言語を設定します。また、検出された全言語の分布を`language_detection`テーブルに保存します（ここでは詳述しません）。

### 3. 日本語書籍のクエリ

言語分析コマンドを実行した後、データベースにクエリを発行して日本語の書籍を特定できます。通常は、`from_metadata_iso639_3`または`from_detection_iso639_3`が 'jpn' であるエントリを探します。

Peewee ORM（メインのREADME.mdで示されているように）を使用したクエリの例は次のようになります。

```python
from models import MainLanguage

# メタデータによって日本語と特定された書籍を検索
japanese_books_metadata = MainLanguage.select().where(MainLanguage.from_metadata_iso639_3 == 'jpn')

# テキスト検出によって日本語と特定された書籍を検索
japanese_books_detection = MainLanguage.select().where(MainLanguage.from_detection_iso639_3 == 'jpn')

# 結果を結合する（例：PythonのセットやさらなるSQLクエリを使用）
for lang_entry in japanese_books_metadata:
    print(f"書籍バーコード (メタデータ): {lang_entry.book_id}")

for lang_entry in japanese_books_detection:
    print(f"書籍バーコード (検出): {lang_entry.book_id}")

```

これらのクエリを適宜変更して、好みの基準（例：検出を重視するか、メタデータを重視するか、あるいは両方の一致を要求するか）に基づいて書籍を選択できます。`MainLanguage`エントリの`book_id`属性は、`BookIO`テーブルの`barcode`に対応します。

## 日本語書籍データのクリーニングに関する一般ガイドライン

日本語の書籍を特定したら、次のステップはOCRで抽出されたテキストの品質と利用可能性を確保することです。日本語テキストには特有の課題があり、特別なクリーニングや正規化の手順が必要になる場合があります。このパイプラインに既存のOCR後処理（`python pipeline.py process ocr-postprocessing step03-process`）は、主にラテン文字ベースの言語用に設計されており、大幅な変更なしに日本語に適用するのは難しいかもしれません。

### 日本語OCRに関する一般的な課題

1.  **文字セットとエンコーディング:**
    *   テキストが一貫してエンコードされていることを確認します（UTF-8が標準です）。
    *   日本語は複数の文字セット（ひらがな、カタカナ、漢字、ローマ字）を使用します。OCRは、似た文字を混同したり、正しい文字セットが認識されない場合にエラーを生成することがあります。

2.  **縦書き（tategaki） vs. 横書き（yokogaki）:**
    *   伝統的な日本語は縦書き（上から下へ、行は右から左へ）で書かれます。現代の日本語では、特にデジタルメディアや技術文書で、横書き（左から右へ）も使用されます。
    *   OCRソフトウェアは、特に文書内で両方のレイアウトが混在している場合や、レイアウト検出が不完全な場合に、テキストの正しいセグメンテーションや順序付けに苦労することがあります。正しい読み順を再構築するのは複雑な場合があります。

3.  **ふりがな（振り仮名）:**
    *   これらは漢字の隣に印刷される小さな表音文字（かな）で、その読み方を示します。
    *   OCRはふりがなを本文の一部として誤って解釈したり、不正確にテキストに挿入したり、省略したりすることがあります。ふりがなを保持するか、分離するか、破棄するかの判断は、下流のユースケースに依存します。

4.  **合字と異体字:**
    *   古い日本語のテキストでは、現代の日本語では一般的ではない異体字（itaiji）や合字が使用されている場合があります。これらを標準形に正規化する必要があるかもしれません。

5.  **句読点と記号:**
    *   日本語の句読点（例：「」、『』、。、）は、西洋の句読点とは異なります。OCRシステムはこれらを正しく識別し、レンダリングする必要があります。
    *   割注（二行にわたる注釈）などの特殊な記号やレイアウト要素も課題となることがあります。

6.  **OCRのノイズとエラー:**
    *   文字の誤認識、文字の結合/分割、ページの汚れや裏写りのようなアーティファクトの混入といった一般的なOCRエラーも同様に発生します。
    *   日本語に特有のエラーとしては、漢字の似た部首の混同や、小さな「かな」の誤認識などがあります。

### 潜在的なアプローチとツール（高レベルな概要）

これらの課題に対処するには、多くの場合、技術の組み合わせが必要であり、特定のツールの実装はこのパイプラインの現在の能力の範囲外です。しかし、以下にいくつかのアプローチを挙げます。

1.  **文字の正規化:**
    *   Pythonの`unicodedata`のようなライブラリを使用して、Unicode文字を正規化します（例：NFC、NFKC）。
    *   一貫性が必要な場合は、半角カタカナを全角カタカナに変換します。
    *   アプリケーションにとって必要であれば、古い文字や異体字を現代の同等な文字にマッピングします。

2.  **レイアウト分析と順序再構成:**
    *   複雑なレイアウト、特に縦書きの場合、OCR出力を単純に一行ずつ読むだけでは不十分なことが多いです。
    *   テキストブロックを正しくセグメント化し、読み順を再構築するためには、文書レイアウト分析に特化したツールやライブラリが必要になる場合があります。（注：このパイプラインには現在、日本語向けのそのような特化ツールは含まれていません。）
    *   文字種（例：文や節の終わりを示す句読点）や行間隔に基づくヒューリスティックスが、部分的な解決策を提供する可能性があります。

3.  **ふりがなの取り扱い:**
    *   文字サイズ（OCRから利用可能な場合）や典型的な配置に基づいて、潜在的なふりがなを識別するためのヒューリスティックスやパターンマッチング（正規表現）を開発します。
    *   ふりがなを削除する、括弧で囲む、または対応する漢字にリンクしようとするなど、戦略を決定します。

4.  **一般的な問題に対する正規表現の利用:**
    *   正規表現は、特定の予測可能なOCRエラーパターンをクリーニングしたり、不要なスペースを削除したり、句読点を標準化したりするのに役立ちます。

5.  **手動でのレビューと修正（サンプリング）:**
    *   高品質なデータセットを目指す場合、特に小規模なコレクションでは、テキストのサンプルを手動でレビュー・修正することで、一般的なエラーパターンを特定し、自動クリーニングスクリプトを改良するのに役立ちます。

6.  **ドメイン固有の辞書:**
    *   書籍が特定のドメインに属している場合、ドメイン固有の辞書を使用することで、専門用語や固有名詞のOCRエラーを修正するのに役立つ可能性があります。

### 既存のOCR後処理フレームワークの利用

現在の`ocr-postprocessing`スクリプトは日本語向けに作られていませんが、フレームワーク自体（テキスト行を分類し、それらを再構成する）は、適応させることが可能です。そのためには以下が必要になります。
    *   日本語テキストの例と、日本語文書に関連する適切な行タイプラベルを使用して、新しい分類モデル（`ocr-postprocessing`のステップ1と2）をトレーニングする。
    *   ステップ3（`step03_process.py`内の`process_book`と`convert_page_chunks_to_text`）で、日本語特有のテキスト特徴を処理するための新しいヒューリスティックスを開発する。

これは大規模な開発作業となるでしょう。現時点では、日本語の書籍を特定し、その後、上記のガイドラインに基づいて外部のカスタムスクリプトをクリーニングに適用することに集中することをお勧めします。

## 日本語書籍の「クリーンデータセット」の作成と管理

日本語の書籍を特定し、任意のクリーニング手順（前のセクションで議論したように、外部のスクリプトやツールを使用する可能性があります）を適用した後、このキュレーションされたデータのサブセットを管理する方法が必要になります。これには、データをエクスポートするか、既存のデータベース構造内でフラグを立てることが含まれる場合があります。

### クリーニング済み日本語書籍データのエクスポート

1.  **データのフィルタリングと選択:**
    *   「日本語書籍の特定」で説明したクエリ方法を使用して、関連する`BookIO`エントリのリスト（例：バーコードによる）を取得します。
    *   クリーニングを実行し、クリーニング済みテキストを（例えば、新しいファイルや別のデータストアに）保存した場合、このクリーニング済みテキストを対応する書籍のバーコードに関連付ける必要があります。

2.  **既存のエクスポートコマンドの利用（カスタマイズあり）:**
    *   パイプラインには、`python pipeline.py export stats overview`や`commands/export/misc/`ディレクトリ内のスクリプトなど、データをエクスポートするためのコマンドが含まれています。
    *   現在、これらのコマンドは既存のデータベースフィールドに基づいてデータをエクスポートします。*クリーニング済み*の日本語テキストをエクスポートするには、おそらく以下の作業が必要になります。
        *   既存のエクスポートスクリプトを修正するか、新しいスクリプトを作成する。
        *   この新しい/修正されたスクリプトは、まず日本語の書籍を特定します（例：バーコードのリストを読み込むか、`MainLanguage`テーブルにクエリを発行する）。
        *   次に、`BookIO.text_by_page`や`BookIO.postprocessed_ocr`から直接テキストデータを取得する代わりに、これらの特定のバーコードに対応する外部でクリーニングされたテキストを取得します。
        *   そして、スクリプトはこのデータを目的の形式（例：CSV, JSONL）で出力します。

    カスタムエクスポートスクリプトのコードスニペット例は次のようになります。

    ```python
    # ('cleaned_japanese_texts'がバーコードをクリーニング済みテキスト文字列にマッピングする辞書であり、)
    # ('japanese_book_barcodes'が関連するバーコードのリストであると仮定します。)

    import csv
    from models import BookIO

    output_data = []
    for barcode in japanese_book_barcodes:
        book_entry = BookIO.get_or_none(BookIO.barcode == barcode)
        if book_entry:
            # クリーニング済みテキストにアクセスします。例：
            # cleaned_text = get_my_externally_cleaned_text(barcode)
            # この例では、辞書に入っていると仮定します
            cleaned_text = cleaned_japanese_texts.get(barcode, "")

            output_data.append({
                "barcode": barcode,
                "title": book_entry.csv_data.get("title_src", ""), # メタデータの例
                "cleaned_text": cleaned_text
                # その他の関連メタデータフィールドを追加
            })

    # CSVに書き出す
    # with open("cleaned_japanese_books.csv", "w", newline="", encoding="utf-8") as csvfile:
    #     writer = csv.DictWriter(csvfile, fieldnames=output_data[0].keys())
    #     writer.writeheader()
    #     writer.writerows(output_data)
    ```

### データベース内でのクリーニング済みデータのフラグ付けまたは保存

あるいは、クリーニングプロセスが標準化されており、クリーニング済みテキストをパイプラインのデータベースにより直接統合したい場合：

1.  **新しいフィールド/テーブルの追加:**
    *   `BookIO`モデル（または関連モデル）に、クリーニング済み日本語テキスト専用の新しいフィールドを追加することができます。これには`models/book_io.py`の修正と、場合によっては新しいデータベースマイグレーションの作成が必要です。
    *   あるいは、`BookIO.barcode`をクリーニング済みテキストやクリーニングプロセスに関するメタデータ（例：使用したクリーニングスクリプトのバージョン）にリンクする新しいテーブルを作成することもできます。

2.  **`BookIO.postprocessed_ocr`の更新:**
    *   もし日本語のクリーニングプロセスを既存の`BookIO.postprocessed_ocr`の構造（`stats`と`text_by_page`を持つ辞書）内に収めることができるなら、`BookIO.postprocessed_ocr`のセッターを適応させて、日本語特有のクリーニング済みテキストを保存することが可能です。
    *   これには、クリーニングの出力がこの構造と一致することを確認する必要があります。その後、`book.postprocessed_ocr = your_cleaned_data_dict`を使用して保存します。
    *   **注意:** このアプローチは、`postprocessed_ocr`が言語によって異なる処理方法からのデータを含むことを意味します。下流のタスクでの明確なドキュメンテーションと慎重な取り扱いが不可欠になります。

### 考慮事項

*   **スケーラビリティ:** 大量の書籍の場合、非常に大きなテキストフィールドをプライマリのSQLiteデータベースに直接保存するよりも、ファイルにエクスポートする方が管理しやすいかもしれません。
*   **バージョニング:** クリーニングプロセスが進化する場合、どの書籍にどのバージョンのクリーニングが適用されたかを追跡してください。
*   **クリーンデータセットの目的:** データの最適な管理方法は、それをどのように使用する予定か（例：直接的な分析、他のモデルへの入力、公開用）によって異なります。

ほとんどのユーザーにとっては、**特定した日本語書籍のデータをクリーニング済みテキストと一緒に別ファイル（例：JSONLやCSV）にエクスポートする**ことが、おそらく最も簡単で直接的なアプローチであり、コアなデータベーススキーマの変更を必要とせずに柔軟性を提供します。
